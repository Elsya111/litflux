# LitFlux

把你对源码的理解直接画成图。保留两张图：业务分解图讲组成，内部流程图讲当前层的因果。**agent 负责解释、实虚线判断和坐标；工具只负责绘制、交互和检查客观缺陷。** 分解和排版建议供你参考，可根据源码与读者需要采用其他自洽的表达，不必逐项申请例外。

开始工作先读 [图的含义](references/mechanism.md)；进入模块编写阶段再读 [作者方式](references/semantic-authoring.md)，对照 [项目模块教学例](examples/project-example.js)。本文件负责工作顺序，机制说明负责图语言，作者方式负责字段、命令与检查边界。

## 工作顺序

按以下六步推进。每步由 agent 对照完成条件自检，满足后继续，不要求用户逐步审批。目标仓库或用户要求有歧义、关键证据缺失且影响解释、需要改变用户指定范围时，说明阻塞点并提问；不影响其他链路的未知项先记录，继续已明确的部分。某阶段因工具或环境受阻时，保留工作材料，按第 6 步报告实际进度与缺口，不将受阻阶段标为完成。

### 1. 明确讲解范围

定位目标仓库，结合用户问题、项目说明、目录和入口配置，列出待追踪的主要能力与入口。确定产品语言和讲解重点；用户未指定深度时，采用机制说明中的默认分解尺度。

在工作记录中简要写下目标、覆盖范围、暂不覆盖的部分和待查问题。复用已有任务记录；没有时可放在 `.litflux/work/notes.md`，不额外建立一套输入模型。

**完成条件：** 已找到与用户问题相关的源码位置，列出本次要讲清的主要功能或处理流程，并标明尚未核实的入口。向用户简述范围后继续，只有上述阻塞情形需要等待答复。

### 2. 追踪真实源码

沿每个待解释入口和生效配置，追踪输入、关键转换、条件与失败路径、输出、资源读写及组件调用。区分默认实现、可替换实现和未确认行为；项目说明与源码不一致时记录差异，解释以查到的实现及配置依据为准。

为关键主张记录文件与行范围。逐项回查第一步列出的能力，标明已追踪、明确不在范围或仍缺证据，避免只沿第一条顺利路径结束阅读。

**完成条件：** 每条纳入讲解的主链能从入口追到结果；影响结果的关键行为有源码依据，尚未确认的部分有明确边界。缺证据的行为保持未知，不编造成确定路径。

### 3. 组织业务解释

先用简短提纲组织工作流与业务层级，再为各层确定输入、处理、判断、结果和必要的资源、组件关系。业务分解解释组成，内部流程解释当前层因果；层级不按目录或函数数量机械生成。

检查每个业务是否仍藏着影响结果的重要选择、转换、组合或外部作用；展开有助于理解时继续，已经讲清且细拆只增加常规操作时停止。逐层对照源码，确认父业务与子图描述的是同一职责，分支条件和数据阶段衔接完整。

**完成条件：** 提纲能讲通每层的输入如何形成结果，关键能力已落到具体业务，展开和停止都有解释上的理由。此时再进入坐标编排；提纲可留在工作记录中，不新增必填交付格式。

### 4. 编写模块与绘制

按作者方式编写一个项目 JS 模块，对象、关系、来源和子业务各定义一次。每条数据边声明 `timing`（immediate/deferred），容易误读的关系可用 `timingNote` 简短说明；中间路径提示供你判断，不决定线型或阻断构建。需要在页面查看源码的对象和关系显式填写来源，具体格式见作者方式。

为每个内部视图编写 `draw(scene, viewport)`，安排主链、分支、坐标、走线和边注；用 `s.nodeBox()` 获取实际节点边界，用 `s.measure()` 测量文字及边注外接框。需要编排思路时可参考[布局参考](references/layout-guidance.md)，也可自行设计。先运行 `--preflight` 检查声明与来源，再构建草稿检查实际绘制；预检不会执行 `draw()`。几何迭代可用 `--geometry-only`，交付前再运行完整检查。

**完成条件：** 声明和来源预检通过，草稿页面能绘制各层对象与关系，没有漏画或绘图异常。几何告警进入下一步修正，不把预检通过当成画图完成。

### 5. 检查与修正

分开核对三件事：解释是否有源码支持、页面是否符合声明和几何要求、读者是否能顺利操作和阅读。先读构建报告，再实际打开页面查看 PC 截图；按 100% 阅读正文，检查主链、分支与边注能否对应。逐个工作流检查阅读和源码查看，有子业务时检查进入与返回，有条件时切换关键情景。

自动检查的具体覆盖见作者方式；截图查看和作者自查另记结果，不能由自动报告替代。

| 发现的问题 | 返回位置与动作 |
| --- | --- |
| 主张缺依据、默认路径不清 | 回第 2 步追源码；保留无法确认的未知项 |
| 业务遗漏、层级或因果关系讲不通 | 回第 3 步修解释，再同步模块及绘图 |
| 字段、来源或绘制错误 | 回第 4 步按具体报错修模块，再预检和构建 |
| 重叠、越界、边注不对应、穿线或文字溢出 | 按报告中的 ID 和坐标修 `draw()`，再构建检查 |
| 报告通过但截图难读或交互异常 | 根据实际页面定位原因，修正后复查受影响视图与操作 |
| 浏览器工具不可用或检查中断 | 保留已有产物，记录未检查项和原因；按实际状态交付 |

每轮修正记录问题、改动和复查结果。反复出现同一问题时先定位原因；不要仅为消除告警删掉必要业务或依赖。模块或绘图变更后重新构建；目标源码发生变化时重新核对受影响的解释与引用，再构建。旧报告和复核材料不能直接充当新产物的证据。

**完成条件：** 已发现的问题已修正并复查，或有明确未解决项和阻塞原因；实际检查范围有记录。存在关键解释缺口或页面问题时，交付须明确说明，不能只报工具状态。

### 6. 交付与说明

提供离线 HTML 链接、建议从哪个工作流开始阅读、实际覆盖范围和剩余未知项，并附构建报告位置。分别说明自动检查、作者源码自查、截图与交互查看、独立复核做了哪些及其结果。

工具状态读取本次构建报告，定义和复核要求见作者方式：`draft`、`checked`、`reviewed`。独立复核只在需要时按该流程进行，不给自己的产物签复核。若工具显示 `checked` 但作者发现解释或视觉问题，照实报告“工具 checked，仍存在……”，继续修正或明确交付为待完善材料。

**完成条件：** 用户拿到可定位的产物、阅读入口、实际验证结果和未完成项。未生成可打开的页面时，只交付工作材料与阻塞说明，不声称已经交付图。

## 运行与工作目录

```sh
python scripts/build_graph.py PROJECT.js OUTPUT --source-root ROOT --draft
python scripts/build_graph.py PROJECT.js OUTPUT --source-root ROOT --review REVIEW.json
```

命令相对技能目录。使用现有 Python 3 与 Node.js（Windows 可用 `py -3`）。浏览器检查使用已安装的 agent-browser，不自动安装。只求值本项目模块，不执行目标项目的应用、模型调用或数据库操作。目标源码只读；工作文件默认 `.litflux/work/`，交付默认 `.litflux/output/`。

## 语言与验证边界

机制、说明和过程记录用中文。产品图文按用户要求（否则按请求语言）编写，模块 `language` 与 `--language` 一致；源码、标识符和路径保留原样。

`checked` 表示本次构建中已实现的声明、几何和交互检查通过，不代表所有操作或情景都已验证，也不证明源码主张真实、解释充分或符合人类视觉。语义、视觉和未覆盖的交互按第 5、6 步另行核对与报告。
